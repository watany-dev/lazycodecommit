# ADR 0009: コメントの下書きと一括投稿

## Status

Accepted. 下書きの作り方、先端が進んだときの扱いなど、判断が分かれる点は
推奨案で書いてあり、決まり次第この ADR を更新する。

## Context

[ADR 0007](0007-out-of-phase-features.md) でフェーズ1〜4の外に置いた「レビュー
画面でコメントを溜めて、まとめて投稿する」に着手する。

CodeCommit には GitHub の「レビューとしてまとめて提出」に当たる API がない。
コメントを書く API は PostCommentForPullRequest（一般とインライン）と
PostCommentReply（返信）だけで、どちらも 1 件ずつ投稿する（SDK のコマンド一覧
にも Batch 系のコメント API はない）。したがって一括投稿は、クライアントが下書き
を持ち、1 件ずつ順に投稿することになる。途中で失敗しうるし、他人には 1 件ずつ
届く。

どちらの API も `clientRequestToken` を受け付ける。API リファレンスによれば
「同じパラメータとトークンの要求は、最初の要求の結果を返す」。違うパラメータで
同じトークンを使うと IdempotencyParameterMismatchException になる。トークンを
どれだけの期間覚えているかは書かれていない。

PostCommentForPullRequest の afterCommitId は「コメントを投稿する時点の、ソース
ブランチの先端」と定義されている。下書きを書いた後に PR の先端が進んだら、
投稿は新しい先端に対して行うことになり、インラインコメントの行番号は書いた
ときと別の行を指しうる。

## Decision

### 下書きを作る（推奨案。確認中）

- c / C / R の入力欄で、Enter はこれまでどおり即時投稿する。Tab を押すと、
  投稿せずに下書きとして保存する。即時投稿の操作感は変えない。
- 下書きモードのような、キーの意味を切り替える状態は持たない。

### 一覧・編集・破棄・投稿

- レビュー画面のヘッダに下書きの件数を出す。インライン下書きは diff の該当行
  の下に、自分の下書きと分かる印で出す。
- D で下書きの一覧を開く。j / k で選び、Enter で該当行に移る、e で編集、
  d で破棄（確認あり）、S でまとめて投稿（確認あり、件数を出す）。
- 投稿は下書きを作った順に 1 件ずつ行う。進捗（2/5 など）を出す。

### 失敗したとき

- 下書きごとにトークン（UUID）を持ち、内容・コミット・位置・返信先が同じ限り
  同じトークンで送る。応答が来ないまま切れた投稿も、再試行で二重に投稿されない。
- 投稿に成功した下書きは、その場で下書きから消して保存する。途中で落ちても
  投稿済みのものを再び送らない。
- 最初の失敗で止める。残りは下書きのまま残し、失敗した下書きに理由を付ける。
  認証切れ、権限不足、スロットリングは後続も同じ理由で失敗するため、続けない。
  S をもう一度押すと、失敗した下書きから再開する。
- 応答の来なかった下書き（タイムアウト、通信断、5xx）は「投稿されたか不明」と
  して印を付け、再試行するまで編集させない。編集するとトークンを作り直すこと
  になり、先の送信が実は届いていた場合に二重投稿になるため。

### 画面を閉じたとき

- 下書きは `~/.local/state/lazycc/drafts.json` に、`<リージョン>/<PR ID>` ごとに
  保存する。他の状態ファイルと同じく 0600 で書き、壊れていたら空として扱う。
- 同じ PR を開き直すと下書きが戻る。下書きを残したまま画面を離れるときは、
  件数を知らせる（確認で止めはしない）。
- 下書きは自分の文字列だが、状態ファイルは端末の外から書き換えられうるため、
  表示前に他人の文字列と同じく無害化する。

### PR の先端が進んだとき（推奨案。確認中）

- 下書きには、書いたときのソースとデスティネーションのコミットと、インライン
  なら該当行の文字列を記録する。
- 投稿の直前に PR を読み直す。先端が進んでいなければそのまま投稿する。
- 進んでいたら diff を読み直し、各インライン下書きの記録した行の文字列が新しい
  先端の同じ行にまだあるかを調べる。あれば新しい先端に投稿する。なければ
  「行がずれた」印を付けて投稿から外し、一覧で場所を確かめてもらう（e で編集、
  d で破棄、または確認のうえそのまま投稿）。一般コメントと返信は行に依らない
  ため、そのまま新しい先端に投稿する。
- 行の対応付け（git diff による行番号の追従）はしない。

## Consequences

- 他人には 1 件ずつ通知が届く。まとめて 1 つのレビューにはならない。
- 一括投稿で新たに要る IAM 権限はない（PostCommentForPullRequest、
  PostCommentReply、GetPullRequest はレビュー画面で既に使う）。
- 同じトークンでの再投稿、先端が進んだ後の再投稿、古い先端への投稿は
  `scripts/realcheck` で実機で確かめる（docs/dev/real-aws-check.md）。モックは
  API リファレンスのとおりに答える。
- トークンの保持期間は文書化されておらず、realcheck でも確かめられない。日を
  またいだ再試行で二重投稿しうることは残る。
