# kick

指定された issue をすべて片付ける。PR は 1 本。issue は作らない。

不明点があれば作業を止めて user に質問する。推奨する回答を添える。コードを
読めば分かることは質問しない。

## 手順

1. **読む**: issue と、関係する `docs/` 配下の仕様・ADR を読み、受け入れ条件を
   issue ごとにまとめる
2. **直す**: issue ごとに失敗するテストを書いてから修正し、1 コミットにする。
   仕様が変わるなら仕様書も更新する。外から来る入力（AWS API の応答、設定
   ファイル、ローカルの git の状態）を扱う形を足すときは、想定外の入力や
   エラーのときにどう振る舞い、user にどう見せるかも決める。黙って握りつぶさ
   ない。`make check` を通す
3. **実機で確かめる**: ビルドした成果物を再現ケースに走らせ、テストが通った
   ことだけで済ませない。CLI はサブコマンドを実際に叩き、テキスト出力・
   `--json`・終了コード（0 / 1 / 2）を確かめる。TUI は `tmux` などで実際に
   操作して画面を確かめる。clone 内と clone 外の両方で振る舞いが変わる機能は
   両方試す。AWS 上のリポジトリやプルリクエストに書き込む操作は、user が許可
   した検証用のリソースに対してだけ行う。隣の不具合や扱えない入力が見えたら、
   軽いものはその場で直し（別コミット）、3 をやり直す
4. **/wrapup** を実行する。修正を取り込んだら 3 をやり直す
5. **PR を出す**: 本文は英語。対象の issue を閉じる。中心は issue から読み取れない
   判断・意図・捨てた案。実機の結果も載せる。diff を見れば分かることは書かない。
   最後に「Found, not fixed」の節を置き、途中で見つけたことを 1 件 1 行で書く
6. **起票しない**: 重いものは 5 の節に書いて終わり。user が必要なものだけ issue に
   する。例外は、再現手順のあるクラッシュかデータを壊す誤動作で、open issue・
   roadmap のどれにも入らないもの。PR 1 本につき 1 件まで
7. **追い続ける**: 15 分ごとに PR を確認し CI を緑に保つ。レビューに追従する。
   merge / close されたらやめる

## 軽い・重い

軽い: 触っている module の中で直せて、仕様を変えず、テスト込みで数十行。見つけた
順に直し、やり直しは合計 3 周まで。重い: それ以外、または 3 周を超えて残ったもの。
